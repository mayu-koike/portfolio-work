# サービス企画書

## 1. サービス概要
美容医療の複数院カウンセリングを回る人向けに、クリニック名・見積金額・ダウンタイムといった基本情報に加え、リスク説明の有無・修正保証・自分の要望との一致度といった、感覚では見落としがちな判断材料を記録・比較できるアプリ。
高額かつ不可逆な意思決定である美容医療の検討において、感覚や記憶に頼らず、自分なりの評価軸で情報を整理しながら判断できるようにすることで、後悔の少ない選択を後押しする。その場の印象や感覚だけで判断してしまいがちな場面で、判断材料を整理・比較することにより、納得感のある意思決定を支援する仕組みである。利用者は個人を想定したtoC向けのサービスだが、設計思想には、情シス実務で培った企業のベンダー選定やSaaS運用における、多軸評価・状態管理の考え方を意図的に取り入れている。

---

## 2. このアイデアはどこから生まれたか
### 2-1. きっかけとなった体験・感情
実際に美容医療のカウンセリングを複数院回っている中で、クリニックごとに提示される施術内容・見積もり・医師の説明がバラバラで、後から「どこが何を言っていたか」を正確に比較できないことに困った。情シスでは、社内OAツールの導入検討(複数ベンダーの比較評価)と、外部ベンダーから導入したSaaSの運用の両方に携わっている。前者では「選ぶ瞬間」に何を評価軸にすべきかを、後者では「選んだ後、実際に使い続ける中で何が重要になるか」を、それぞれ別の立場から実感してきた。その考え方を個人の意思決定の場面にも応用できるのではと感じたのがきっかけ。

### 2-2. なぜそれが「気になった」のか
業務上、意思決定は感覚ではなく評価軸を並べて比較すべき、という考え方が身についていることに加え、大学で認知心理学を学んでいたことも影響している。認知心理学や行動経済学で扱われる二重過程理論では、人の判断には、直感的・自動的に行われる過程と、情報を整理しながら意識的・論理的に考える過程があると説明されている。特に金額が大きく、後戻りしにくい意思決定では、目の前の印象だけで判断せず、複数の判断材料を比較しながら慎重に検討することが重要だと考えた。美容医療はまさにこの条件が揃っているにもかかわらず、実際のカウンセリングではその場の説明に流されて判断しがちだと感じ、専門知識と実体験が結びついたことがこのアプリの発想の根底にある。

## 3. 課題の整理(表面的になっていないか)
### 3-1. 表に見えている困りごと
カウンセリングの内容を、あとから正確に比較できない。

### 3-2. 本当に解決したい課題は何か
- なぜ困る？①: メモの取り方がクリニックごとにバラバラだから
- なぜ困る？②: 比較すべき軸(価格・信頼度・ダウンタイムなど)を事前に決めずに聞きに行っているから
- なぜ困る？③: 情報収集と意思決定の「型」を持たず、その場の説明に流されて判断してしまうから
**本当に解決したい課題:** 高額な意思決定の場面で、自分なりの評価軸を持って比較検討できていないこと

## 4. 想定ユーザーについて
### 4-1. 想定しているユーザー
- 年齢: 20代後半〜30代前半
  - 理由: 経済的にある程度自己判断で高額な自由診療を検討でき、かつ複数院のカウンセリングを回る行動力がある年代のため。
- 生活・状況: 仕事をしながら、平日夜や週末にカウンセリング予約を入れて複数院を回っている人。美容医療は一つの施術で終わらず、次の悩み・部位の検討へ連鎖的に広がりやすい特性があるため、単発ではなく継続的に検討・比較が発生する。
- 利用環境: カウンセリング前後や外出先ではスマートフォンで情報を入力・確認し、自宅での情報整理や比較、ダッシュボードの確認にはPCも利用することを想定している。

### 4-2. 自分とユーザーの距離
自分自身。実際にカウンセリングを回っている当事者であり、実体験に基づいて機能や評価軸を設計できる。

### 4-3. 実際に使われる可能性について(需要・存在確認)
- 最初に使ってくれそうな人: 自分自身、友人
- 使う場面: 次のカウンセリング予約前や、複数院の内容を比較して迷ったタイミング
- 代替手段: メモ帳アプリ、LINEキープメモ、スプレッドシート
- 置き換える理由: 評価軸が固定フォーマットで毎回入力でき、比較ビューで横並びに見られる点が既存の汎用メモにはない価値

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ
- きっかけ: カウンセリング予約が決まったタイミングで、比較のために記録を始める
- 最初の一歩: アカウント登録後、直近で回ったクリニックを登録
- 利用の流れ: カウンセリング直後にその場でスマートフォンから記録を入力し、検討中の複数院がたまった段階で一覧画面を開き、評価項目を横並びに比較しながら次の一手を判断する
- 継続理由: 美容医療関連事業者の自主調査には、経験者の多くが今後も施術を希望していることや、複数回施術を受けていることを示す結果もある(聖心美容クリニック調べ、トリビュー調べ)。ただし、業界主体の調査であるため参考情報の域を出ないものの、美容医療が一度きりで終わらないケースも一定数あると考えられる。

## 5. 既存サービス・競合調査
### 5-1. 似たサービスの調査
- サービス名:トリビュー(美容医療の口コミ予約アプリ)
- URL: [https://tribeau.jp/](https://tribeau.jp/)
- どんなことができるか:クリニックの検索から予約、口コミ・症例写真の閲覧、施術やクリニックについての質問・カウンセリングなど、他の利用者が投稿した情報をもとにクリニック選びを進められるプラットフォーム。累計ダウンロード数は150万を超える規模。

- サービス名: MEMUU(美容医療の記録)
- URL: [https://apps.apple.com/jp/app/id6760345034](https://apps.apple.com/jp/app/id6760345034)
- どんなことができるか: カウンセリングや施術の記録を一元管理できるアプリ。日付・クリニック・医師・費用・メモなど、事実の記録が中心で、判断・比較のための構造化項目は持たない。

- サービス名: W/Beauty(美容医療特化型記録アプリ)
- URL: [https://apps.apple.com/jp/app/id6526479396](https://apps.apple.com/jp/app/id6526479396)
- どんなことができるか: 施術記録・費用・保証・契約書まで一元管理でき、AIチャットで施術後の不安を相談できる。ただし、施術前に使える主な機能はAIとの対話であり、複数院を構造化して比較する機能はない。

### 5-2. それでも自分が作りたい理由
既存アプリ(トリビュー・MEMUU・W/Beauty)は、「他人の情報を見る」「施術内容を記録する」「AIに相談する」ことには対応しているが、複数院を、リスク説明の有無・修正保証・要望との一致度などの構造化された判断軸で横並びに比較する機能は持たない。本アプリは、この「決める前の比較」に焦点を絞ることで差別化している。

### 5-3. 差別化を「体験価値」で表現する
私のアプリの差別化ポイント: 複数院を比較検討している人が、価格だけでなく、リスク説明の有無・修正保証・自分の要望との一致度など、カウンセリングで確認した情報まで含めて横並びに整理できること。

## 6. このサービスで提供したい価値
### 6-1. ユーザーの変化
- 行動の変化: カウンセリング内容をその場の印象だけで判断せず、共通の評価項目で記録・比較できるようになる
- 気持ちの変化: 「あとで比較できる」という安心感を持ってカウンセリングに臨める
- 考え方の変化: 高額な意思決定を、感覚だけでなく整理された情報に基づいて判断する習慣がつく

### 6-2. 価値を一文で表す
このサービスは、**複数のクリニックを比較検討する人**が、**価格・ダウンタイムに加え、リスク説明の有無・修正保証・自分の要望との一致度なども整理し、納得感のある意思決定をできるようにする**サービスである。

## 7. このアプリで実現すること
設計思想としては、情シス業務で扱ってきたCRMの考え方を、クリニックの比較検討に応用している。CRMで顧客情報・商談履歴・ステータスを管理するように、本アプリではクリニック・カウンセリング記録・検討状況を管理する。利用者が評価軸に沿って各院の情報を整理し、比較・検討できる構造にした。

### MVPで実装した機能（実装済み）
- ユーザー認証(ユーザーごとのデータ分離)
- クリニックの検討記録のCRUD(登録・一覧・詳細・編集・削除)。一覧では主要な評価項目を列に持つ表形式にし、複数院を横並びで見比べられる最低限の比較体験をMVPの段階で検証する

**主な記録項目**
- 基本情報: クリニック名、担当医、カウンセリング日、施術部位
- 管理項目: 検討状況ステータス、補足メモ
- 検討内容: 悩み・希望、提案施術、提案理由、見積金額、ダウンタイム、効果持続期間、修正保証の有無
- 5段階評価の項目: リスク説明の誠実さ、提案内容の納得感(=自分の要望との一致度)

MVPは5-3の差別化の核(価格・リスク説明・修正保証・要望との一致度)に評価軸を絞り、医師の説明の丁寧さなど残る5段階評価項目や、核に含まれない医師の資格・所属学会の確認情報は本リリースに回す。自由記述も悩み・希望、提案理由、補足メモに絞り、それ以外は選択式や段階評価を中心に構造化することで、比較・絞り込みがしやすいデータ構造にしている。詳細なカラム名やデータ型は、ER図・詳細設計で定義する。

---

### 本リリースで作る機能
MVPで「記録して一覧で見比べる」ことができるようになったため、本リリースでは「カウンセリング前に準備し、記録をもとに比べて決める」までをできるようにする。
- **カウンセリング前の事前準備**：予約の時点で記録を作ると、予算・休める期間や確認すべきことのリストができ、当日はスマートフォンでチェックしながら聞ける。チェックした内容はカウンセリング後の入力に引き継がれる
- **評価項目の拡充**：「リスクの説明があったか」などの事実（はい／いいえ）と、「説明の分かりやすさ」などの印象（1〜5）を分けて記録する
- **比較スコアリング**：費用・ダウンタイム・誠実さ・医師と提案の4つのカテゴリに重みを付け、スライダーで重みを変えるとクリニックの順位がその場で入れ替わる
- **認知バイアスへの対策**：当日契約を勧められた院には注意の印を出す。予算オーバー・期限切れの院は条件外として表示する。比較の前に記録した「第一印象の本命」が何位になったかを表示する
- **マイページ**：予算・休める期間・重視したい項目（重み）を設定する
- **ダッシュボード**：検討院数・平均見積額・ステータス別の件数・予算との比較・評価軸ごとの平均をグラフで表示する
- **カレンダー**：施術予定日からのダウンタイムを表示し、休める期間に収まるかを確認する
- **比較レポートの出力**：部位ごとに複数院の評価をまとめたレポートを、印刷・PDFで保存できる

**主な記録項目**
記録は「カウンセリング前の事前準備」と「カウンセリング後の記録」の2段階で入力する。カウンセリングの直後でも無理なく入力できるよう、カウンセリング後の記録は必須の項目を先に表示し、それ以外は「詳しく入力する」で開く形にしている。

- カウンセリング前の事前準備
  - 基本情報: クリニック名、部位、カウンセリング予定日、施術（任意）
  - 事前に整理すること: 悩み・希望、その他に聞きたいこと（自由記述）
  - 確認すべきことリスト: 予算・休める期間（マイページの設定から自動で表示）、評価の事実の項目、その他に聞きたいことを一覧で表示し、当日に聞いた項目へ印をつける
- カウンセリング後の記録
  - 提案内容: 提案された施術、提案理由、担当医
  - 費用: 見積額（割引後）、最終的な支払総額（手数料・麻酔代など込み）、割引前の価格、支払い方法（一括・分割）、支払い済みの費用、無料と言われたもの、見積もりの有効期限
  - 経過・保証: ダウンタイム（日数）、効果の持続期間（月数）、修正保証（なし・条件付き・あり）、施術予定日
  - 事実の確認（はい・いいえ・未確認）: リスク・副作用の説明、費用の内訳の提示、解約・返金の条件の説明、医師本人の診察、執刀医が分かるか、当日契約を勧められたか、持ち帰って検討してよいと言われたか
  - 印象の評価（1〜5、各段階に説明文あり）: 説明の分かりやすさ、希望を聞いてくれたか、提案の納得感
  - メモ: 気になった点（必須）、補足メモ
  - 管理項目: 検討状況のステータス、第一印象の本命
- マイページで設定する項目: 予算（1回の施術にかけられる上限）、休める期間（複数登録可）、重視したい項目の重み（費用・ダウンタイム・誠実さ・医師と提案）

**DB構成**
本リリースでは、`users`・`clinics`・`treatments`・`counseling_records` に加えて、`evaluation_axes`・`record_scores`・`user_category_weights`・`vacation_periods` の8テーブルで構成する。

MVPでは、クリニック名・施術名をマスタとして切り出すため、`clinics`・`treatments` を `counseling_records` から分けた。クリニックは個人の行動履歴に近い機微な情報のため `clinics` に `user_id` を持たせてユーザーごとに管理し、施術は医学的な一般名称であり客観的な情報のため、全ユーザー共通の読み取り専用マスタ（`db/seeds.rb` で管理者が管理）としている。

本リリースでは、評価項目を1項目1カラムで持つ形をやめ、`evaluation_axes`（評価軸のマスタ）と `record_scores`（記録ごとの評価）に分けた。評価項目を増やすたびにカラムを追加する必要がなくなり、比較スコアリングで評価軸ごとに重みを掛ける計算もしやすくなる。評価軸は「事実（はい／いいえ）」と「印象（1〜5）」に分けて持ち、印象の項目には1〜5の各段階の説明文を持たせている。修正保証は「なし・条件付き・あり」の3択のため、評価軸ではなく記録のカラムとして持つ。

ユーザーごとの重みは `user_category_weights`、休める期間は `vacation_periods` に持たせ、予算は `users` に持たせている。部位は記録ごとに選ぶ形とし、施術マスタとは紐付けていない（ヒアルロン酸注入のように複数の部位で使う施術があるため）。

身体・医療に関わる機微な個人情報を扱うため、検討記録は本人にのみ紐づけて非公開とし、他ユーザーからは参照できない設計とする。将来的な機能拡張においても、第三者への共有・公開を前提としない範囲で検討する。

**ER図の補足**
- 評価の持ち方
  - 評価項目は `evaluation_axes`（マスタ）と `record_scores`（記録ごとの評価）に分けて持つ。評価項目を増やしてもテーブルを変えずに済む
  - `evaluation_axes` は `db/seeds.rb` で管理者が管理する全ユーザー共通のマスタ。`key` はプログラムから参照する固定の名前で、画面に出す `name` を変えても影響が出ないようにしている
  - 修正保証は「なし・条件付き・あり」の3択のため、評価軸ではなく `counseling_records.revision_guarantee` に持つ
- スコアの計算
  - 重みは評価項目ごとではなく、4つのカテゴリ（費用・ダウンタイム・誠実さ・医師と提案）ごとに `user_category_weights` に持つ
  - 費用・ダウンタイムは `counseling_records` の値、誠実さ・医師と提案は `record_scores` と `revision_guarantee` から点数を出す
  - カテゴリが「注意の印」の評価項目（当日契約を勧められた など）は、スコアには含めず、印として表示する
- 事前準備とカウンセリング後の入力
  - ステータスが「カウンセリング予定」の記録は、事前準備の段階。施術（`treatment_id`）は任意で、カウンセリング後の入力で必須にする
  - 「カウンセリング予定」の記録は、比較画面とダッシュボードの集計から外す
  - `checked_items` には、確認すべきことリストで聞いた項目を、評価軸の `key` と「その他に聞きたいこと」の行番号でまとめて保存する
- 予算と休める期間
  - 予算は1回の施術にかけられる上限として、`users.budget` に1つだけ持つ
  - 休める期間は `vacation_periods` に複数持てる。施術予定日があればその日を含む休み、なければ一番長い休みの日数とダウンタイムを比べる
- 一意制約
  - `record_scores`：（`counseling_record_id`, `evaluation_axis_id`）
  - `user_category_weights`：（`user_id`, `category`）
- 部位と施術
  - 部位（`treatment_area`）は記録ごとに選ぶ。施術マスタとは紐付けていない（ヒアルロン酸注入のように複数の部位で使う施術があるため）

## 8. このアプリの懸念点とその対策
### 懸念点①
- 何が問題になりそうか: 市場全体の需要の大きさは検証できていない
- なぜそう思うか: 美容医療の検討頻度は高くなく、既存のメモアプリやスプレッドシートで代替されている可能性がある。また、既存の記録アプリはあるものの、複数院を評価軸で比較する機能への需要がどの程度あるかは確認できていない
- そのために考えている対策: まずは自身の実体験に基づく課題解決と、要件定義・DB設計の示し方に軸足を置く。今後、必要に応じて簡易アンケートの実施も検討する

### 懸念点②
- 何が問題になりそうか: 身体・医療に関わる機微な個人情報を扱うため、情報漏洩や意図しない第三者への公開が起きた場合の影響が大きい。
- なぜそう思うか: 検討記録には、悩み・希望や医師とのやり取りなど、他人に知られたくない情報が含まれる可能性が高く、汎用的なメモアプリ以上に非公開性への配慮が求められる。
- そのために考えている対策: 検討記録は本人アカウントにのみ紐づけ、他ユーザーや第三者からは参照できない設計とする。認証(Devise)によるユーザーごとのデータ分離を徹底し、共有・公開機能は本リリース以降もスコープに含めない方針とする。悩み・希望などの入力内容を外部のサービス（AIなど）に送る機能も、現時点では採用しない。エラー監視（Sentry）でも、個人情報を送らない設定にしている。

## 10. 技術スタック(手段としての技術)
### 10-1. 使用予定の技術
- フレームワーク: Ruby on Rails
- フロントエンド: Hotwire(Turbo + Stimulus)
- CSS: Tailwind CSS(tailwindcss-rails)
- DB: PostgreSQL
- 認証: Devise
- グラフ: Chartkick + Groupdate
- テスト: RSpec、FactoryBot、SimpleCov（カバレッジ測定）、Bullet（N+1の検出）
- CI: GitHub Actions（RSpec、RuboCop、Brakeman）
- エラー監視: Sentry
- デプロイ先: Render

### 10-2. 技術選定の比較検討
**Ruby on Rails(Hotwire含む) → 採用**
- フロントエンドも含めてRails単体で完結でき、規約重視の設計によりCRUD実装を素早く形にできる
- JS/CSSの管理もアセットパイプラインとImportmapで完結するため
- 比較スコアリングのスライダーのように、操作に合わせて画面をその場で更新する部分は、Stimulus で実装できる

**Next.js / React → 余裕があれば検討（本リリースでは不採用）**
- メイン機能（事前準備・比較スコアリング・ダッシュボード）の実装完了を優先するため、本リリースは Rails + Hotwire で作成する
- スコア計算や集計のロジックは service に分けておき、将来フロントエンドを移行するときも、ロジックをそのまま使えるようにしている

- 今回チャレンジしたい点: 単なるCRUDに留めず、集計ダッシュボード・多軸比較スコアリングといった、業務システム的な設計パターンを実装すること
- 不安な点: 比較スコアリングのDB設計(評価軸・重み付けの持ち方)がやや複雑になる可能性がある
  - → 評価軸を `evaluation_axes`、記録ごとの評価を `record_scores`、ユーザーごとの重みを `user_category_weights` に分けて持つことで、評価軸を増やしてもテーブルを変えずに済む形にした

### 10-3. キャッチアップ不足の懸念
本リリースまでを Rails + Hotwire で完結させる方針にしているのは、新しいフレームワークの習得に時間を取られて開発が遅延するリスクを避けるためでもある。使い慣れた技術で確実に完成させることを優先し、Next.js / React への移行は本リリースの後に検討する
